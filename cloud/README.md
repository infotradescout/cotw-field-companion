# Browser-only phone relay

This optional, operator-enrolled preview serves the existing companion interface over HTTPS. The PC makes an outbound WebSocket connection only after the owner enables Phone access. It does not open the local companion to the LAN or change game-save permissions. No second map, account database, raw game-save upload, or cloud journal is created. Public self-service player enrollment is a separate product requirement; this preview does not provide it.

## Runtime and deployment

- Node 22.13+; `npm ci --prefix cloud --ignore-scripts`, then `node cloud/server.mjs`.
- Set `PHONE_RELAY_SIGNING_KEY` to a persistent 32-byte random base64url value. Generate it securely once, store it as a provider secret, and never commit or log it. Startup refuses a missing or malformed key. Changing it invalidates all device credentials and phone sessions.
- Set `PHONE_RELAY_ORIGIN` to the exact public HTTPS origin, or use Render's supplied `RENDER_EXTERNAL_URL`. `PORT` defaults to 10000 and the cloud service binds to `0.0.0.0`. The private PC application remains bound to loopback.
- The Blueprint in this folder is a prepared candidate. Creating a service still requires the intended Render workspace and deployment authorization; do not attach it to another product or use another product's database.
- [Render supports HTTPS and WebSockets](https://render.com/docs/web-services). The [free plan](https://render.com/docs/free) has a shared workspace allowance of 750 instance hours per month, idle wake-up delays, ephemeral local storage, and bandwidth/build limits. Additional bandwidth may be billed. Verify the workspace's current allowance and spending controls before deployment. This is not unlimited free hosting or a continuous-uptime promise.
- Run one relay instance. Connections, outstanding requests, pairing links, and rate limits are bounded in memory. Multiple instances require a separately designed shared routing/authentication boundary.

## Private installation enrollment

The operator must enroll each PC installation before its first enable. `cloud/auth.mjs` exports `createPhoneEnrollmentToken({key, installationId?, expiresAt?})`: call it in a private operator environment with the relay signing key, a distinct random 32-byte base64url installation identity (generated by default), and an expiry no more than one year away. Deliver the resulting signed permit privately to that PC as `COMPANION_PHONE_ENROLLMENT_TOKEN`. Keep the relay signing key on the operator/service side; it is never needed on the PC. Do not print either secret in logs or put the permit in a public app, portable build, `phone-service.json`, browser assets, or a repository file. There is no public enrollment-minting endpoint.

The local backend sends the permit only as `Authorization: Bearer <permit>` on `POST /phone/device` with an empty JSON object. Missing, malformed, expired, and wrong-purpose permits are rejected. Provisioning is limited per installation and replaces the installation's previous active identity. Saved signed device credentials reconnect without resending the enrollment permit; a fresh enable after disable needs a still-valid permit.

## PC integration

`lib/phone-bridge.mjs` exports:

```js
const credential = await provisionPhoneDevice({relayUrl, enrollmentToken}); // Only after local enable.
// Persist credential.deviceToken in the companion's own private data directory.
const bridge = createPhoneBridge({
  relayUrl,
  deviceToken: credential.deviceToken,
  readState: reserve => observer.state(reserve),
  runCommand: body => scopedLocalCommand(body),
  onStatus: status => updateLocalPhoneStatus(status),
});
await bridge.connect();
const pairing = await bridge.pair(); // {url, expiresAt}; do not log this bearer link.
await bridge.close();
```

The **local-only**, existing token-protected routes are `GET /api/phone/status`, `POST /api/phone/enable`, `POST /api/phone/pair`, and `POST /api/phone/disable`. Phone relay configuration is never a remote command. Disable closes the bridge and deletes the stored device credential; the next enable provisions a fresh identity. `close()` alone is for normal app shutdown and permits reconnecting with the saved credential.

## Public feedback service (separate candidate)

`feedback-server.mjs` is a separate, opt-in service for the public companion's feedback loop. It does not run as part of the phone relay and it does not receive game saves, journal exports, screenshots, or account identifiers. It stores only bounded plain-text feedback in a configured SQLite database and exposes an authenticated owner inbox. See [`FEEDBACK-SERVICE.md`](../FEEDBACK-SERVICE.md) for the contract and [`render-feedback.yaml`](./render-feedback.yaml) for a candidate Render shape. Neither is deployed by the existing phone-relay Blueprint; the service URL, persistent disk, owner token, origin policy, and live owner journey must be accepted separately.

Local persistence and enable/disable controls are owned by the main companion integration. The bridge library reads no files and does not enable itself. Its tests use disposable state.

## Privacy and credential model

Each enrolled PC receives a random identity with a purpose-bound, signed device credential, valid for no more than one year or the enrollment permit's remaining lifetime. The WebSocket upgrade supplies the protocol marker and credential in subprotocol headers; the relay authenticates before accepting the socket or counting it against PC capacity. It echoes only the protocol marker. Anonymous connections cannot occupy an authenticated slot. At most one socket per installation is active, and reconnecting the same identity remains possible at full capacity.

A pairing link has a 256-bit secret in the URL fragment, is stored hashed at the relay, expires after five minutes, and can be consumed once. The connection page immediately removes the fragment from browser history. Pairing is deliberate: the user presses Connect on that page.

The paired browser receives a signed 30-day `HttpOnly; Secure; SameSite=Strict` cookie. API reads require the owner's cookie; writes also require the exact origin, a session-bound CSRF token, bounded JSON, and an allowed companion operation. Requests route exclusively through that owner's live socket. A replacement socket needs a valid device credential for the installation and invalidates outstanding requests from the previous socket. Commands are never automatically retried; retained request IDs preserve the PC journal's existing idempotency behavior.

The signing key preserves device/browser pairing across relay restarts. In-progress pair links do not survive a restart. Phone sessions are bearer credentials, not email accounts or global account authentication. Disabling locally rotates the next device identity; old cookies cannot reach the newly enabled PC. The live relay rejects older signed installation generations once a newer one is provisioned or connected. That generation record is in memory: after a relay restart, a copied old credential can occupy its old identity until the current PC reconnects, and the newer generation then replaces it. It cannot access the new PC's data. This is not durable, global credential revocation. Clear browser cookies on a lost/shared phone and disable/re-enable on the PC to create a fresh pairing boundary. Replacing an exposed enrollment permit does not invalidate its old signed copy; rotating the relay signing key provides immediate service-wide invalidation and requires fresh permits and pairing for every installation.

No private data is requested before enabling the PC bridge and pairing a browser. Only the explicit presentation projection crosses the connection: map marks, saved hunting summaries, career counters, and companion journal entries. Raw parser payloads, account/profile identity, save paths, checksums, health diagnostics, and raw error strings are excluded. `observer.sources` includes allowlisted source names, timestamps, status, and generic errors only. Public map/catalog metadata is loaded from the same repository. Export is explicitly a projected phone view, not a raw/full PC journal backup.

## Offline and failure behavior

The PC must stay powered, online, and running the companion. No cloud history is retained. A current browser may keep its last visible view, but the interface must identify it as stale when the PC disconnects and disable writes. A new/reloaded browser cannot recover offline player data from the relay.

The bridge reconnects with bounded delays. Render can [close connections during deployment or maintenance](https://render.com/docs/websocket); a new socket cannot complete an old socket's request. A timed-out mutation has an unknown outcome: refresh before retrying, and retain the request ID if deliberately retrying the same operation. No retry path modifies game saves.

## Acceptance boundary

Run `npm test --prefix cloud` plus the companion's unchanged full suite. Before real deployment, independently review authentication, projection, resource caps, owner isolation, and local enable/disable. Live acceptance needs a synthetic PC profile and a real phone on cellular: pair, open all existing views, read fresh state, make a disposable journal change, disconnect/reconnect the PC, and verify another browser/device cannot read that owner's state. No production phone journey is implied by local tests.
